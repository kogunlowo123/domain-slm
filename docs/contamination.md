# Contamination

The gate this project exists for, and the measurement that shaped it.

## The problem

A reported accuracy is a claim about data the model has not seen. When part of
the evaluation set is also in the training set, the number is partly a
memorisation score — and **there is no way to tell from the number itself**. A
contaminated 96% and a clean 96% are the same number.

So the only defence is to measure the overlap directly, before believing either.

```bash
dslm contamination --train splits/train.jsonl.gz --evaluate splits/test.jsonl.gz \
  --null holdout.jsonl.gz --drop-shared
```

## How overlap is measured

**N-gram containment**, not Jaccard similarity. The two answer different
questions:

- *Jaccard* asks "how similar are these two records?" — symmetric, and diluted
  by everything the evaluation record contains that the training record does
  not.
- *Containment* asks "what fraction of this evaluation record's n-grams appear
  **anywhere** in training?" — which is the actual question. A record whose
  every phrase the model has already seen is not a test, however long it is.

The training side is one set of every n-gram it contains. That is the right
shape — the model saw all of training, not one record at a time — and it makes
the check affordable: one pass to build the set, one probe per record.

## Why the published threshold does not transfer

The usual rule is *"13-gram containment ≥ 0.5 is contamination"*, from the
technical reports of several published models. This project inherited it and
measured it.

The `holdout` corpus is generated by the same grammar with a different seed, so
it shares no record with training **by construction**. Scored against training:

| Corpus | Hit rate at the published rule |
| --- | --- |
| `holdout` — cannot be contaminated | **1.80%** |
| the genuine test split | **1.25%** |

Data that cannot be contaminated scores *higher* than data that might be. The
rule cannot even order the two correctly, so a threshold applied to its output
decides on noise.

Nothing is wrong with the arithmetic. Maintenance write-ups are formulaic —
whole clauses are standardised — so two entirely different work orders routinely
share a thirteen-word run. **The rule is measuring how formulaic the domain
is.** On web-scale prose, where it was calibrated, that background is near zero
and the rule works.

Restricting the index to *distinctive* n-grams (those in exactly one training
record) halves both numbers and leaves the ordering just as wrong: 0.54% for
test against a 1.13% background. The background is a property of the domain, not
of the index.

Reproduce all of this with `python examples/contamination_demo.py`.

## What replaces it: calibrating the threshold

Score a corpus known to be disjoint, and take a high quantile of *that*
distribution as the threshold — the containment level disjoint data essentially
never reaches. On the shipped corpus that is **0.846**, not 0.5.

```
threshold 0.846 at the 99.9% quantile of 1500 disjoint record(s);
the published 0.5 threshold would call 1.6% of them contaminated
```

The quantile is a promise about how often disjoint data will be called
contaminated. 0.999 rather than 0.99: at p99 a clean split still shows a small
non-zero rate, which is a floor under every measurement the gate makes.

### The result: a measurement, not a flag

With records copied verbatim from training into test at a known rate:

| Injected | Measured |
| --- | --- |
| 0% | 0.00% |
| 5% | 4.89% |
| 10% | 9.96% |
| 25% | 25.00% |

Within 0.11 points. `scripts/check-pipeline.py` asserts this on every push, and
`tests/meta/` asserts it at three rates with a clean control at the same
threshold.

### The design that was tried first, and why it failed

The original version calibrated the *rate*: compare the evaluation set's hit
rate against the null's, and fail on the excess. It was measured, and it was too
blunt. A clean split sits *below* the background, so contamination had to climb
past it before the gate noticed — **a 10% verbatim injection passed**.

Calibrating the threshold instead makes the reported rate mean what it says.
The failure is recorded because the fix is not obvious from the outside.

## When there is no null corpus

The tool reports the raw rate and **refuses to gate on it**:

```
the hit rate is 0.36% at an uncalibrated threshold, and there is nothing
that says what that means for this data.
  Supply a null corpus that shares no record with training (--null <corpus>) ...
```

That refusal is the design, not an inconvenience: a number nobody can interpret
is not a gate. `--allow-uncalibrated` opts back into the published rule for text
where it genuinely applies — a deliberate act, visible in a command line and in
a diff.

## Choosing a null corpus

It must share **no record** with training, and that is checked rather than
trusted — one set operation against the alternative of a gate that is quietly
lenient in exactly the situation it exists for.

Three ways to get one:

1. **Hold data out before the pipeline runs.** The best option when you have it.
2. **Generate it**, as this repository does, from the same process with a
   different seed.
3. **A later time period** — next month's records, if the domain is stable.

Two corpora from one grammar with different seeds really can produce the same
sentence: the shipped holdout collides with training on one record in 1,500.
`--drop-shared` removes those and **reports how many**. It is off by default and
has to be asked for, because a null corpus that silently shrinks is one nobody
would think to question.

## The other way this check fails

A 13-gram is longer than many records, and **a check whose n-gram never fits is
a check that always passes.** So the report carries coverage, and the gate
refuses a split where most of the evaluation set was too short to examine:

```
only 31.2% of the evaluation set was long enough for a 13-gram check;
the minimum is 50%.
```

"The check did not apply" and "the check passed" are different facts. Lower
`--ngram-width` to suit your records — but do not read the result as clean.

## What the gate does when it fails

Not a warning above a number. **No number at all.**

```json
{
  "passed": false,
  "trustworthy": false,
  "contamination": { "rate": 0.178, "threshold": 0.846, "calibrated": true },
  "refused": "99 of 552 evaluation record(s) (17.93%) also appear in training..."
}
```

There is no `metrics` key. The Markdown summary says why instead of printing a
figure, and the JUnit XML has a failing case. A warning above a number is read
as a number.

## Settings

| Setting | Default | What it does |
| --- | --- | --- |
| `DSLM_GATE__QUANTILE` | 0.999 | Quantile of the null used as the threshold |
| `DSLM_GATE__MAX_CONTAMINATED` | 0.02 | Hit rate allowed before the gate fails |
| `DSLM_GATE__MIN_COVERAGE` | 0.5 | Fraction that must be checkable at all |

The limit is not zero on purpose: one duplicated record in a thousand does not
invalidate a measurement, and a gate that fails on it is a gate someone will
disable.
